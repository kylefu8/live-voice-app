# Live Voice App project guidelines

- Read README.md for confirmed requirements, proposed choices, and acceptance criteria. CONTEXT.md contains domain terms only.
- This is a separate voice-app project with Android and Windows clients. Keep changes inside live-voice-app/ except necessary updates to the umbrella project index. Preserve demo/ and its private configuration.
- The current milestone is Android native validation in native/, alongside the simulated browser prototype in prototype/ and real local encrypted QR generation in pc-config/. Native connection tests and sessions use real network calls; Android 0.2.0 adds camera QR import, local decryption, masked review, explicit probes and an atomic encrypted connection save. Keep build/unit-test and PC QR decode evidence distinct from device camera, audio, and provider verification; local verification reports are ignored. Preserve the documented QR v1 wire format and fixed vectors.
- Android is the first delivery platform; retain an iOS path. Validate the actual native audio and live-session protocol before committing to a framework.
- The phone connects directly to configured model services. The PC generates encrypted configuration QR codes; it is not a runtime relay.
- The standalone PC web tool's connection tests run only on explicit clicks through its loopback Node service, using transient supplied credentials. Keep that test route same-origin, bounded, cancellable and free of raw provider errors or credential logs; its QR encryption and passphrase stay in the browser. The Windows desktop client instead uses a sandboxed renderer and a narrow main-process bridge with system-encrypted credential storage; only encrypted QR payloads leave the main process. Neither PC application is a phone conversation relay.
- desktop/ is the approved Electron Windows client. Android and Windows histories remain local to each device; phone linking exports connection configuration only. See docs/adr/0001-windows-client.md and desktop/CONTRACT.md.
- Use standard authenticated encryption with a user-supplied string passphrase. Never embed a shared decryption password or place the passphrase in the QR payload.
- Do not put API keys, real endpoints, decrypted profiles, QR images containing real configuration, recordings, or transcripts in source, logs, or test fixtures.
- Do not disclose the user's specific phone models, personal device names, serial numbers, or device identifiers in replies, tool output, tracked files, screenshots, commit messages, or release notes. Use generic labels such as "Android test device" and "iPhone test device". Keep identifiers needed for local deployment only in ignored local files, and redact them from output.
- Use synthetic configuration for tests. Distinguish cryptographic round-trip tests, mocked session tests, and real-device/provider verification.
- User-facing documentation and new UI copy must support Chinese and English. Identify Live Voice as a client for the GPT-Live-1 model; distinguish the separate backend LLM. Publish only screenshots generated from synthetic data, with personal metadata removed. Keep Windows and mobile download links visible together in the latest release.
- Natural conversation and interruption are core acceptance criteria. Verify them on physical devices, including speaker echo and Bluetooth routing.
- Avoid adding accounts, a relay backend, course systems, or shared packages without a concrete requirement.
